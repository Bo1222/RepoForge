# 批量 Coding Agent 的验证驱动修复优化方案

日期：2026-10-21。状态：设计已确认，业务实现与效果验证待开展。

本方案分析现有优化逻辑，并明确后续实现的行为、边界、默认值和验收场景。本次交付仅新增设计文档并更新 CHANGELOG，不实施运行代码、不调用模型、不启动实验、不修改既有实验锁和结果。

## 1. 目标、范围与证据

### 1.1 优化目标

主线是建立“可靠执行事实 → 当前补丁的验证证据 → 失败解释 → 定向干预 → 再验证”的闭环。重点改善测试目标、证据有效性和可恢复执行，让每次测试为下一步修复提供信息。

范围限定为批量执行路径，暂不涉及 CLI。用户已选择分级交付：允许保存部分验证或验证受阻的补丁，但必须说明验证范围与限制。答案生成与独立判题继续隔离。

预期改善是减少确定性工具失败、无效重试、错误完成声明与无依据的重复动作。修复率和成本收益均待后续独立验证，不预先承诺增加多少 resolved。

## 2. 原方案合理性与必要修正

统一执行事实、绑定补丁版本、失败驱动修复和优先优化 query-time 检索，均有合理依据。以下边界必须修正：

| 原设计 | 风险 | 本方案决定 |
| --- | --- | --- |
| 所有异常转 ToolResult，继续 job | 掩盖工作区损坏、恢复冲突或程序缺陷 | 仅结构化预期执行失败；取消、恢复冲突和状态不确定保留退出路径 |
| terminal_safe 决定继续 | 工具不了解全局预算和恢复状态 | 工具报告副作用、一致性和清理事实；控制器决定继续、恢复或退出 |
| no-op 不消耗执行步 | 重复拒绝可能绕过预算 | 不计有效编辑，但计入调用、生成轮次、费用和重复次数 |
| AST 判定真实测试 | 遗漏框架、参数化、动态收集及 doctest | AST 只生成候选，由仓库 runner 确认收集与执行 |
| 新增测试必须跑同目标 base_public | base 中没有该文件 | 新测试做基准/补丁对照；既有公共测试另选目标 |
| tested_patch_hash 必须等于 product_patch_hash | workspace 执行补丁可能合法地包含测试修改 | 记录执行配方，分别绑定产品、测试和环境 |
| receipt 中更新 STALE | 破坏不可变审计记录 | receipt 保持不变，当前有效性按版本推导 |
| confidence=0.86 | 未校准，容易被误读为正确概率 | 保存相关性特征和证据等级，首版不输出概率 |
| 原公共测试全绿是唯一完成条件 | 对符合新需求的补丁产生假阴性 | 分级交付，保留旧期望冲突证据 |
| 目标失败称 F2P，公共回归称 P2P | 混用独立判题标签 | 运行期使用“复现仍失败”“公共回归”等名称 |
| query-time BM25 无需成本 | 仍需词项统计、索引构建和失效管理 | 用已有 chunks 懒构建 lexical 索引并缓存 |
| 无 import/命名关联即拒绝 | 静态分析可能漏检 | 相关性用于候选排序，不能单独证明无关或成功 |

累计文件覆盖高不代表及时命中正确函数、代码范围和测试；低 Recall@1 也可能来自查询和过滤问题。现阶段优先优化 fallback 合理，但不能认定现有索引已经没有改进空间。

同样，“测试后继续修复”是已有范式。本项目可解释的贡献应体现为目标选择、版本绑定、失败分类、预算约束和干预选择如何形成可靠闭环。

## 3. 工具契约、编辑、超时与 retry

### 3.1 兼容式执行契约

保留现有 [Observation](../moatless/actions/schema.py)，新增带版本的 `properties.tool_result`。通过适配器读取旧的 fail_reason、return_code、test_status 等字段；旧轨迹缺失的信息记为 unknown，不能补造成功。

契约分开表达以下内容：

- 执行状态：完成、参数拒绝、超时、执行错误。
- 业务结果：测试通过/失败/未知，编辑成功/无变化等。
- 失败证据：类别、文件、范围、测试标识、错误摘录和 source_id。
- 副作用与一致性：是否修改、进程清理是否完成、工作区能否确认一致。
- 重试建议：由控制器结合预算和历史作决定，不由工具自动无限重试。

断言失败属于一次已完成的测试执行，不能当作模型协议失败。无法确认进程停止、补丁恢复或持久化状态时，进入既有恢复/终止路径。不得将取消或未知异常统一转换成“可重试成功返回”。

### 3.2 编辑：预检—候选校验—提交

1. 规范化路径并检查当前内容版本，沿用仓库访问边界。
2. 文件存在但不在 FileContext 时，自动登记并加载匹配范围附近代码，标记 auto_loaded；文件过大时不将整文件加入模型请求。
3. 文件不存在返回 not_found 和有界路径建议；零匹配返回附近候选，多匹配返回位置，要求模型补充准确原文。候选只用于反馈，不自动模糊替换。
4. old_str 与 new_str 相同时提前返回 no_changes，保留真实计数，不产生有效编辑或验证失效。
5. 在内存构造完整候选文件，使用目标任务环境的 Python 解释器进行不执行代码的编译校验。错误返回行列与附近片段，不提交。
6. 无法使用目标解释器时明确标记未检查，不把宿主解释器的结果冒充目标环境兼容结论。非 Python 首版仅使用已有解析器给出诊断，不新增强制阻断。
7. 提交前再次确认源版本，发生冲突则拒绝；提交后更新指纹，返回 compact diff 和检查状态。

AST 成功不保证后续编译成功，因此不能仅凭 ast.parse 标记语法完全有效，见 [Python AST 文档](https://docs.python.org/3/library/ast.html)。编译成功也不证明运行或业务正确。

产品输入变化使相关验证过期；workspace 测试变化使相应 workspace 证据过期。原始公共测试 receipt 是否有效，取决于它实际执行的输入是否变化，不能只因任意测试编辑而全部作废。

同路径连续失败达到两次后，不重复盲改，交给失败控制器安排读取或 replan。

### 3.3 超时：统一所有者，清理完成后继续

当前存在 Agent、Flow 和底层测试多层超时。后续由一次工具调用的 deadline 统一分配，避免外层 120 秒先打断底层 600 秒的处理。

首版每次验证运行一个模块；执行预算沿用有效工具预算，默认 120 秒。外层兜底上限为执行预算加 10 秒清理宽限，Agent 与 Flow 不再设置相互竞争的同值计时器。基准对照属于单独记录的测试执行，不在一个已耗尽的调用中隐式加跑。

超时后先终止进程组、回收进程、取得现有输出并恢复测试工作区，再返回 timeout、partial results、timed_out 和未完成目标。只有工作区一致性可确认时才继续修复。清理超过宽限或状态不确定时进入恢复/退出。

Runner 支持单用例选择时才允许缩小到用例；不支持时维持模块级目标，不静默删除选择器后声称跑过该用例。用户取消继续传播，不转为普通超时后自动重试。

### 3.4 Retry：完整归档，有界反馈，重新投影

现有 [completion retry](../moatless/completion/base.py) 会追加完整无效 assistant 响应。应保留原文审计记录，在下一次请求内仅放置有界纠错信息。

- 无工具调用：保留校验原因和必要短摘录；空内容不重复加入请求。
- 有工具调用：维护全部调用与结果配对，未执行调用不得描述成成功执行。无法合法重用的残缺调用不执行，重新请求。
- 协议纠错最多两次，瞬态网络错误最多一次；单次生成总尝试最多三次，由一层统一计数。认证、余额、明确参数错误不作为瞬态网络故障重试。
- 每次发送前计算完整请求，超预算时重新选择可选上下文；必选内容仍超预算才明确失败。
- 被拒绝请求记录估算 tokens、预算、拒绝原因和脱敏引用，不输出凭据。

沿用现有输出上限与安全余量，初始投影额外预留 512 tokens 纠错空间，不再重复扣除一份输出预算：

    有效输入预算 = min(输入上限, 上下文窗口 - 配置输出上限 - 安全余量)
    初始投影预算 = 有效输入预算 - 512

512 是首版设计默认值，不是实测最优值；重试请求仍必须受有效输入预算约束。所有失败尝试、no-op、拒绝和重试计入实际预算。

## 4. 验证目标、不可变 receipt 与分级交付

### 4.1 三种类型与三个状态维度

新增以下概念，扩展现有 [TestRunRecord](../moatless/execution_memory.py)，避免另造互相矛盾的事实来源：

- VerificationTarget：目标、runner、选择依据、相关产品范围。
- VerificationReceipt：一次真实执行的不可变记录。
- VerificationSummary：根据当前输入版本及多个 receipts 推导的当前状态。

不将所有信息压成一个线性状态枚举。每个目标分别维护：

| 维度 | 状态 |
| --- | --- |
| 可用性 | 未发现目标、可执行、不可用 |
| 新鲜度 | 当前有效、过期 |
| 结果 | 未运行、通过、失败、不完整、未知 |

一个目标通过不能覆盖另一个相关目标仍然失败的事实。验证过期不修改历史 receipt，而是改变当前 Summary。

### 4.2 目标发现与有效性

候选来源按问题相关性使用：公开失败记录、issue 中的符号/行为、搜索命中、既有测试命名、AST/import 关联。AST 和命名不作为唯一准入标准，最终依赖仓库 runner 的收集和执行能力。

每个候选保存“为什么与当前改动相关”的特征；最多执行两轮发现。没有有效候选时明确不可用，不以无关测试的全绿替代。

目录和 pattern 可以作为发现输入，但实际执行必须解析成明确模块；用例标识只有 runner 支持时才接受。首版一次执行一个模块。

### 4.3 执行配方与 receipt

Receipt 至少保存：

- 基准提交、当前产品补丁 hash、实际执行补丁 hash。
- 实际测试内容、辅助输入及验证配置指纹。
- runner、命令、目标、环境指纹和执行时间。
- 收集/执行数量、各类状态、退出码、超时与 partial 标志。
- 稳定测试标识、失败摘录、原始输出 source_id。
- 基准对照引用、比较是否有效及失败差异。

校验的是“此次执行配方是否与当前要求一致”，不是简单要求 tested_patch_hash 等于 product_patch_hash。workspace 配方可以包含测试修改；base_public 配方使用原始公共测试和产品补丁。

验证配置、conftest、测试辅助文件等也属于验证输入；不能仅依赖文件名识别测试。普通输出文件和测试缓存不应无条件使 receipt 过期，但产品代码、相关数据、测试配置及环境的变化必须纳入判断。

### 4.4 三路验证

| 路径 | 执行内容 | 证明范围 |
| --- | --- | --- |
| 原始公共回归 | 基准公共测试内容 + 产品补丁 | 选定既有行为的回归情况 |
| 新增/修改后的任务测试 | workspace 测试 + 当前产品代码 | 当前任务测试在当前工作区的结果 |
| 问题复现对照 | 同一公开复现/测试分别运行在基准产品和补丁产品上 | 原问题是否在基准失败、在补丁后通过 |

新测试不存在于 base 时，不把它作为同目标传给 base_public。应将同一新增测试单独放入对照运行，再选择既有相关公共测试检查回归。只有公开问题与代码可用于构造复现。

只有同目标、同测试内容、兼容环境且基准执行完整时，才比较 introduced_failures。稳定标识包括可获得的文件、类、用例及参数信息；名称缺失、收集失败、环境不一致或基准不完整时比较状态为 unknown，introduced_failures 为未知，不能用空数组表示无回归。

退出码为零、确有测试执行、解析可信、结果完整且没有超时，才能认定一次运行通过。全 skipped、零收集、解析空结果、未知结果和非零退出都不能标记通过，见 [pytest 退出码说明](https://docs.pytest.org/en/stable/reference/exit-codes.html)。

### 4.5 分级交付与 Finish Guard

| 交付状态 | 条件 |
| --- | --- |
| verified | 当前版本有相关任务验证通过，选定公共回归证据完整，且没有未解释的相关失败 |
| partially_verified | 有有效通过证据，但覆盖/对照不足，或存在有公开需求依据的旧测试期望冲突 |
| verification_unavailable | 发现、收集、环境或持续超时阻止有效验证 |
| budget_exhausted | 全局预算不足以继续，保存当前补丁及最后证据 |
| rejected | 没有可交付修复，或当前条件下无法完成 |

Finish 是交付请求，控制器根据证据确定状态。流程结束仍是 terminal；terminal 不代表任务成功。无修复补丁不得声明修复成功，但可以清楚地退出。

相关失败触发 repair，过期证据触发重新验证。原测试期望与 issue 冲突时，必须保留公开需求、基准/补丁行为和相关测试证据，不能仅凭模型声称就排除失败；不能自动回退合理的测试修改。

Verified 仅表示约定范围内的本地验证。resolved/local_resolved 只能来自冻结答案后的独立判题。公共测试通过与隐藏测试仍失败可以同时发生，本方案不承诺消除这一客观差异。

相关性只保留可解释特征和证据等级，不输出未经校准的概率。

## 5. FailureInterpreter 与有界修复控制器

FailureSignal 包含类别、失败测试、相关文件、错误摘录、版本、来源和稳定 signature。分类不确定时保持 unknown。

| 信号 | 默认干预 | 必须保留的限制 |
| --- | --- | --- |
| collection/import/syntax | 读取诊断及相关文件，区分产品、测试、runner 和环境来源 | ImportError 不自动等于缺依赖 |
| assertion_failure | 保留 expected/actual，定位产品行为并定向修复 | 重跑目标由 runner 能力决定 |
| product_exception | 读取相关栈帧、代码和当前 diff | 产品栈帧本身不足以证明补丁归因 |
| 公共回归 | 同条件基准对照，确认后 repair/revert | 对照未知时不得声称 introduced regression |
| 复现仍失败 | 带失败行为进行定向修复 | 不使用官方 F2P 标签作为运行期输入 |
| test_timeout | 缩小目标或做基准对照，至多追加一次同类尝试 | timeout 自身不能证明环境问题或产品挂起 |
| no_test_target | 公开代码候选发现，最多两轮 | 无关目标通过不能代替任务验证 |
| 测试修改/新增 | 分开记录 workspace、对照及公共回归 | 不自动视为作弊或强制回退 |
| environment_error | 判断基准是否同样受阻，保存环境证据后退出或执行明确的环境处理 | 不因环境噪声无依据修改产品代码 |
| protocol_error | 有界纠错；仍失败则退出 | 不记录成工具成功 |
| no_progress/repeat | 改变读取、查询、验证或修复方式 | 不是成功信号，也不直接代表无解 |

反馈携带失败类别、测试、关键诊断、当前产品文件、来源和推荐下一步；避免泛泛的“换一个动作”。确定性控制器可安排安全读取/验证，具体产品编辑仍由模型基于证据提出，不从失败类别机械生成修改。

同一失败族允许两次定向修复，仍重复时执行一次有证据的 replan；之后仍无新增有效证据则带当前状态退出。同路径连续编辑失败两次时也应转读取/replan。计数不能仅因 patch hash 或测试目标变化而重置。

失败族由稳定类别、测试行为和归一化诊断识别，版本作为关联信息另存。新定位、排除假设和缩小失败范围也属于进展，不要求每次都改变 patch 或目标。全局费用、轮数、取消和恢复约束优先。

## 6. 检索 fallback、融合与版本管理

### 6.1 查询与候选链

确定性提取 backtick 标识符、CamelCase/snake_case、qualified name、路径、错误字符串和 definition/usage/test 意图，不额外调用查询理解模型。

1. 精确符号/字符串命中优先。
2. 无有效命中时启用归一化 symbol、fuzzy 和路径候选。
3. 仍不足时执行 lexical 与 dense 检索，并融合排名。
4. 显式文件过滤保持有效；放宽过滤作为单独建议，不静默改变用户查询范围。

FindCodeSnippet 接入统一 fallback 结果契约，避免独立路径直接返回无帮助的空结果。

### 6.2 融合默认值

首版使用 RRF，不直接相加 BM25 分数、向量距离、排名和 import 距离：

    score(document) = sum(1 / (60 + rank_in_retriever))

每路最多 25 个候选，最终最多 10 个片段，每文件最多 3 个。同分按路径和起始行稳定排序。精确命中优先；单行命中按输出预算扩展到相关函数/类范围，不能无界扩展整个大类。

RRF 使用各路排名合并不同检索信号，参见 [RRF 文档](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)。上述数量是首版工程默认值，尚未实测调优。

Fixture、docs、vendor 和 __init__.py 按意图降权，不统一过滤；明确精确命中应保留。改动文件加分只能作为相关性提示，不能阻止发现真正应修改的其他文件。

### 6.3 成本、缓存与输出

从既有 docstore chunks 懒构建 lexical 索引并缓存，按语料版本失效；更新或新增文件使用增量覆盖，删除文件移除。Dense 历史结果需检查当前文件版本，旧片段不能作为最新代码返回。

阶段内不重做 embedding 或 chunking，不新增 reranker 服务；没有依赖图时跳过图扩展，不伪装已有图能力。

输出包含路径、行号、符号、命中依据、fallback 路径和版本。已查看且同版本的片段可返回 compact 引用；版本变化必须展示当前内容。最终确实无候选时允许明确 no-hit，路径建议与真正内容命中分别标注。

## 7. 闭环所需的上下文治理

本阶段只纳入与当前修复相关的确定性治理，不引入 LLM 滚动摘要或长期向量记忆。

- 当前有效失败保留测试名、断言差异、关键产品栈帧、receipt 范围和 source_id；大量通过用例聚合。
- 相同路径、版本和重叠行范围的 read/current_code 去重；同文件多个相关范围保留，不能只保存最后一次 view。
- 去重按最终选入请求的消息执行，避免删掉 current_code 后对应 read 也被裁掉。
- 提供有界来源目录，使用可直接传给 ReadObservation 的 node_id:step_index 引用，附工具、文件、摘要、版本和有效行范围。
- stale/dedup 说明汇总，原始输出继续归档；所选历史工具调用和结果仍合法配对。
- execution_facts 优先呈现当前相关文件、有效测试和未解决失败；旧版本事实改为归档引用，不能让必选块随历史无限增长。
- 按工具类型保留诊断，再使用通用头尾裁剪兜底。旧用户约束和适用规则不得仅因时间久而删除。

选择优先级为：有效需求/规则、当前验证与必要代码、最近完整交互、相关搜索/假设证据、其他历史和来源目录。保留选择原因与分类 token 占用，便于审计。

## 8. 实施顺序、兼容与验收

### 8.1 后续代码实施顺序

| 阶段 | 内容 | 完成标志 |
| --- | --- | --- |
| 1 | 兼容式工具结果、retry 预算、统一超时清理 | 确定性失败能分类；重试有界；超时后的状态可信 |
| 2 | 编辑预检、候选编译校验、提交版本检查 | 无效编辑不写入，no-op 有真实计数 |
| 3 | 公共目标发现、receipt、基准对照 | 当前补丁的验证证据可追溯；未知不冒充无回归 |
| 4 | 分级交付、失败解释及干预控制器 | 失败能够驱动下一步，结束与成功分离 |
| 5 | 检索融合、增量覆盖、上下文投影 | 检索和历史证据能为闭环提供及时的当前内容 |

各阶段使用新配置显式启用，旧 T7 锁、profiles 和历史结果不被覆盖。旧轨迹缺失信息读取为 unknown，不追认 verified。新记录和策略显式版本化；恢复时重新比较当前输入，不能直接复用 checkpoint 中的 verified 标记。

### 8.2 未来实现的最低验收场景

以下是行为验收清单，不代表本次已经实现或执行测试：

1. 自动加载、路径不存在、零/多匹配、no-op、语法拒绝和提交冲突均不会错误写入。
2. 编译检查使用目标环境；检查不可用不会显示已通过。
3. 产品、相关测试或环境改变后，旧证据不会被错误复用；缓存输出不引发无依据的全面失效。
4. 新测试能进行同测试内容的基准/补丁对照；既有公共回归独立记录。
5. 零测试、全 skipped、未知解析结果、非零退出、partial 和 timeout 不产生通过声明。
6. 基准对照缺失、不完整或测试标识无法对应时，回归结论为 unknown。
7. 原测试期望冲突有需求与执行证据时可部分交付；不能由模型一句声明自动豁免。
8. 超时保留现有结果，进程和工作区清理可验证；清理失败进入恢复/退出，取消不被吞掉。
9. 接近输入上限的无效响应重试不追加整条内容；多工具调用保留合法配对，总尝试有界。
10. 重复失败有界退出；单纯变更 patch hash 或目标不能清零次数；新定位可以被识别为进展。
11. 精确搜索和显式过滤不被 fallback 破坏；lexical 缓存反映新增、修改和删除文件。
12. 原始输出保持可回读，目录引用有效，去重后当前必要代码仍可见。
13. 旧轨迹、checkpoint 和禁用新配置的既有行为保持兼容。
14. 生成路径不能读取隐藏测试、官方判题标签、参考补丁或独立判题缓存。
