# 批量 Coding Agent 的验证驱动修复优化方案（A0 / O2 fixed）

日期：2026-10-22。最终架构：**A0 base + O2 fixed（a5）**。

本文只描述最终保留的两套架构及 O2 fixed 相对 A0 的优化。历史上的 A6 acceptance-repair 与 A7 single-controller 仅保留在 preservation commit `ccb91158`（分支 `preserve-agent-architectures`），不属于最终代码路径，也不进入最终简历条目。

## 1. 最终架构

| 架构 | 定义 | 用途 |
|---|---|---|
| **A0 base** | `code_and_test` agent + `LangGraphFlow`，`action_policy={"variant":"off"}`；模型自行读代码、编辑、RunTests、`VerifiedFinish` | 基线 |
| **O2 fixed（a5）** | A0 + `ActionPolicy` 反馈控制；`submit_product_only=True` | 最终版本 |

O2 fixed 不引入新的 agent 工具或 system prompt：模型侧仍是 A0 的 `code_and_test`（`SemanticSearch/FindClass/FindFunction/FindCodeSnippet/ViewCode/StringReplace/CreateFile/AppendString/RunTests/VerifiedFinish/Reject`），没有 acceptance plan、ReplanRepair、CheckSyntax、ExplainTestConflict，也没有 test observation barrier。优化只发生在控制器的 `policy_decision` 与执行事实层。

## 2. Pipeline 变化

### A0

```text
prepare_iteration
  -> generate_actions (model tool calls)
  -> policy_decision (variant=off，直接 execute)
  -> execute_action
  -> record_observation
  -> commit / policy（模型继续下一批动作）
```

- 测试由模型显式调用 `RunTests`；没有控制器插入的验证或动作拦截。
- 结束时 `VerifiedFinish` 返回 terminal observation；`agent.py` 用 `classify_completion` 计算内部 `completion_status`。
- 导出完整 patch（测试编辑也可能包含）。

### O2 fixed

```text
prepare_iteration
  -> generate_actions
  -> policy_decision
       ActionPolicy(a5).decide(state, proposed_step, budget):
         allow / replan / verify / stop
  -> execute_action
  -> record_observation
  -> policy / commit
```

关键变化：

1. **每次 propose 前计算 `PolicyState`**（`extract_state`）：当前产品补丁、动作签名、进度/no-gain、repeat 窗口、`edits_since_test`、可用测试 target、`TestRunRecord` 与 verification snapshot、failure signal。
2. **控制器可以选择不执行当前 proposal**：`replan` 把当前响应剩余 step 标为 skipped，保留原始 action/proposal_id，并写入 `node.policy_feedback`。
3. **控制器可以插入验证**：`verify` 追加一个 policy-origin `RunTestsArgs(test_files=[target], test_source="base_public")`。
4. **控制器可以停止**：`stop` 设置 terminal + 内部 `completion_status=unverified` + `finish_reason=policy_stop`。
5. **`VerifiedFinish` 按 terminal 处理**：修复前只认 `Finish`，生产 agent 的 `VerifiedFinish` 没有触发“无产品 patch 停止”和“finish 前验证”分支。
6. **导出只含产品补丁**：`submit_product_only=True`；`select_submitted_patch` 只返回当前产品补丁，不回退历史绿补丁。

## 3. ActionPolicy 具体算法

### 3.1 输入特征（`extract_state`）

- `signature = content_hash(action, 相关文件版本/workspace 版本, environment)`；全局搜索使用 workspace 版本。
- 遍历 trajectory 中所有非 skipped observation：
  - 产品编辑且 workspace 实际变化 → progress；
  - 新 code view（动作签名 + 输出 hash）→ progress；
  - 新 test receipt（targets/test_source/status/counts/product_patch_hash）→ progress，并重置 `edits_since_test`；
  - search hits 进入 candidate test targets；
  - 连续无 progress → `no_progress++`；`progress_reset_after` 可重置。
- `repeat_count`：在最近 `repeat_window=8` 个动作中，与当前 signature 相同且 no-gain 的数量。
- `replan_attempts`：`policy_state.replans[signature]`。
- **target 选择**：优先模型显式 `test_files`；其次最近测试/context/discovered 候选；非显式 target 必须与变更产品文件有名称或 import 关联；必须是存在且可执行的测试模块。
- `verification_snapshot`：当前产品 hash 的 records 是 passed/failed/stale；`base_public` passed 且无 introduced failure → `PUBLIC_VERIFIED`；当前测试失败 → `TESTED_FAIL`；没有绑定当前 patch → `STALE`。
- `interpret_failure`：把最后 observation 映射为 collection/assertion/product/timeout/no-target 等信号及建议动作。

### 3.2 决策规则（a5）

| 顺序 | 条件 | 决策 |
|---|---|---|
| 1 | `cost_complete=false` | `stop unknown_cost` |
| 2 | terminal（`Finish`/`VerifiedFinish`）且无产品 patch | `stop no_product_patch` |
| 3 | 与上一个动作 signature 相同且 failure signature 相同 | 未 correction → `replan`；已 correction → `stop` |
| 4 | `repeat_count >= 2` 或 `no_progress >= 4` | 先给一次验证/repair：有 target → `verify`，否则 `replan need_public_test_target`；已有 replan 记录 → `stop` |
| 5 | `needs_check` | 见下 |
| 6 | budget reserve | `stop budget_reserve` |
| 7 | 其他 | `allow eligible` |

`needs_check` 的三个来源：

- terminal + 有产品 patch +（未 public verified 或当前测试失败）；
- 有产品 patch、当前不是 RunTests，且 `edits_since_test >= threshold`；threshold 在 changed_product_files > 1 或 current_test_failed 时为 1，否则为 3；
- budget reserve + 有产品 patch + 未 public verified。

`needs_check` 分支：

- `current_test_failed` 且未 corrected → `replan`（repair，跳过当前 proposal）；
- 已 corrected → terminal/budget 时 `stop verification_unavailable_or_failed`，否则 `allow verification_already_attempted`；
- 无 target → `replan need_public_test_target`；
- 有 target → `verify`（policy 追加 base_public RunTests）。

### 3.3 预算与状态

- `BudgetSnapshot`：`remaining_rounds = max_iterations - 已创建 node 数`；`spent_cost` 来自 SDK recorder；`cost_complete=false` 时不能继续；`low_cost` 用下一次调用的保守估算。
- `correction_key = hash(product patch hash, target, environment)`：同一 correction 只允许一次，防止重复验证/重复失败。
- `policy_state`：`corrections`、`replans`、`progress_reset_after`，跨 node 持久化，支持 resume。
- 所有 controller 决策写入 `node.policy_decisions`；拒绝的模型 proposal 保留为 skipped observation，不执行、不伪装成功。

### 3.4 执行事实与验证

- `TestRunRecord v3`：targets、test_source、product_source、return_code、counts、results、`input_identity`、`test_bundle_hash`、`base_identity`、`runner_fingerprint`、environment、complete/timed_out/patch_stale。
- `effective_status` 由当前输入重新推导；产品/测试/环境变化 → stale。
- base/current 对照只在同一 target、同一 test bundle、同一 runner/environment 且执行完整时比较 `introduced_failures`；否则 unknown，不用空数组冒充无回归。
- 产品补丁导出与判题隔离：answer patch 只含产品修改；测试修改不进 patch；官方 Harness 不进入生成上下文。

### 3.5 环境前置（不是算法）

pytest-7490 的旧 native pilot 在 exact-base shallow clone 下生成 `src/_pytest/_version.py=0.1.dev1`，低于 `pyproject.toml` 的 `minversion=2.0`，导致 agent 本地 `RunTests` 在收集前 rc4。最终使用方案 A：

- 用当前 `NativeProvisioner`（`SETUPTOOLS_SCM_PRETEND_VERSION=6.0`）在 `/tmp/A7_reprovision_20261022T123738Z` 重新 provision pytest；
- 新 receipt 通过 `--provision-override` 合并；
- `src/_pytest/_version.py=6.0`，agent patch 不含 `_version.py`。

这是 testbed/harness 修复，不计入 O2 算法，也不应进入简历的“算法优化”条目。

## 4. 简历条目

> 以下数字来自历史 5 个 SWE-bench Verified smoke 实例的本地 native sanity；不是新 split，官方 Harness 为 `not_run`。A0 为历史基线运行，O2 fixed 为最终单次运行，二者不是受控配对实验；简历中应保留“sanity”与“local resolved”限定。

### 4.1 项目一句话

- 在批量 Coding Agent 中加入确定性的 **验证驱动动作控制**：A0 基线 3/5 → O2 fixed **5/5 local resolved**，成本基本持平（A0 $0.354 / 121 步；O2 $0.3556 / 125 步），且不改变模型工具与 prompt。

### 4.2 简历项目条目（可直接改写的要点）

- **批量 Coding Agent 验证控制（A0 → O2 fixed）**
  - 设计并实现 `ActionPolicy`：在每个模型 proposal 前计算产品补丁、动作签名、no-progress/repeat、测试 target 和预算，输出 `allow/replan/verify/stop`，不额外调用模型。
  - 提出 verification-first 规则：无进展/重复时先验证再停止；编辑阈值（1/3 次）与预算 reserve 触发 `base_public` 验证；失败测试触发定向 repair replan，而非重复同一验证。
  - 实现执行事实与版本绑定：`TestRunRecord v3` 记录完整 test recipe、base/current 对照、runner/environment；只有同输入、同 bundle、完整执行才比较 introduced failures。
  - 实现产品-only 导出：answer patch 排除测试修改，去掉历史绿补丁自动回退；`VerifiedFinish` 纳入 terminal，finish 前验证与无 patch 停止生效。
  - 结果：5 个历史 smoke 实例从 A0 **3/5** 提升到 O2 fixed **5/5 local resolved**；最终单次运行 $0.3556 / 125 步、13 次 test process、0 error；O2 fixed 组合基线 $0.3774 / 105 步，成本 −5.8%、步数 +19%。
  - 说明：5 个实例为 smoke sanity，不是新 split；官方 Harness `not_run`；内部 `completion_status` 为 1 verified / 4 unverified，`local_resolved` 5/5 来自独立 native grading。

### 4.3 面试可讲的 pipeline

1. 模型 propose 动作；
2. `extract_state` 从执行事实计算补丁版本、no-gain/repeat、edits、target、verification snapshot；
3. `ActionPolicy.decide` 决定 allow/replan/verify/stop；
4. `replan` 跳过当前 proposal 并写反馈，`verify` 插入 base_public RunTests，`stop` 记录 unverified reason；
5. 执行后 `after_action` 生成不可变 TestRunRecord，下一轮重新计算；
6. 最终只导出当前产品补丁，独立 grading 判 F2P/P2P。

### 4.4 边界与限制

- 内部 `completion_status` 不是官方 resolved：它来自 controller 的本地 test records/snapshot；O2 最终 4/5 因 policy stop 记为 unverified，但 native `local_resolved` 为 5/5。
- 历史 5 题不是新 split；A0 3/5 与 O2 5/5 不是同一受控运行；成本/步数为项目参考口径。
- O2 没有 acceptance plan/checkpoint/ReplanRepair gate；这些属于历史 A6/A7，不在最终架构。
- 官方 Harness `not_run`；不宣称 hidden-test 正确率。
